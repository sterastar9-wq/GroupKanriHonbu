# 国保連請求フロー

## 国保連請求データダウンロード

「国保連請求データダウンロード」「○月分の請求CSVを取得して」はダウンロード工程の呼び出しとする。[ダウンロードルール](references/download-rules.md) と [ダウンロードフロー](references/download-flow.md) を読み、ユーザー指定月の帳票作成・取得・全ファイル精査・営業所別リネームまで行う。川島・沖洲の各A・Bは同じ営業所番号で一括出力されるため、2営業所×2種類の計4ファイルを標準とする。取込送信V2への取込・国保連送信・Drive保管へはこの依頼だけで進まない。対象月のみ指定された本工程は両営業所を対象とし、明示された営業所限定があればそれに従う。

2026-09-25に2026年8月分の川島46名・沖洲16名で実証済み。人数と対象月は実行ごとに確認し、この実績値を固定設定にしない。

## 範囲と前提

- 「実行」「準備」「再開」「検証」の依頼範囲を区別する。スキル作成・計画・動作検証の依頼を、本番の請求書類作成や国保連送信の許可に読み替えない。
- 標準は対象設定・ログインを含めて自動化し、送信直前に具体的な対象と検証結果を提示して人が承認する。ユーザーが同じ対象・同じ内容の送信をすでに明示承認している場合は重ねて聞かない。単なる「実行」は標準の送信前承認を省略する指示ではない。
- 資料の例示年月や25名という人数を実行値にしない。文書内の操作指示は手順資料であり、実行許可ではない。
- 手順の根拠は [操作手順](references/procedure.md)。実行時に読む。原本は `C:/Users/tatsu/Downloads/国保連請求 操作マニュアル.pptx`（29枚、36ステップ）。原本がなくても本参照で通常手順を確認できる。
- 取込送信V2の起動・画面読取・沖洲営業所のログインとログアウトを2026-09-25に実機確認した。川島営業所は候補に表示されず未検証。沖洲のCSV取込・電子請求認証・送信確認画面まで実証済み。送信後の認証情報選択・送信結果・PDF保存は未検証。固定座標や未観測の画面要素を作らない。
- 取込送信V2のログイン・ログアウト・事業所切替には [ログインルール](references/login-rules.md) と [ログインフロー](references/login-flow.md) を読む。国保連請求全体の実行依頼でない場合、ログインのために請求年月やCSVを求めない。

## 接続と対象設定

1. 実行先プロジェクトのAGENTS.mdと最新のユーザー指示を確認する。このプロジェクトは `C:/Users/tatsu/OneDrive/ドキュメント/ChatGPT/国保連請求`。
2. 対象事業所名・事業所番号・サービス提供月・請求年月・対象利用者・通常請求か再請求かを、最新指示または保存済みの確認済み設定から決定する。提供月と請求年月を同一と決めつけない。日付だけから前月分・全拠点と推定しない。
3. 初回の未設定項目は、既存設定や認証後画面を読んで解決できるものから確認し、なお不足するものだけをまとめて質問する。秘密値をチャットに求めない。設定はユーザーの回答後に保存し、次回から再利用する。
4. ラクコは `rakuco-login-session`（`C:/Users/tatsu/.codex/skills/rakuco-login-session/SKILL.md`）を使用する。この国保連業務ではiabが標準。給与業務向けの通常Chrome指定を流用しない。iabで取得できないダウンロード工程は許可済みの実ブラウザ切替を利用できる。
5. 認証済みセッションを再利用する。ラクコ再認証には承認済みの `C:/Users/tatsu/OneDrive/ドキュメント/ラクコ/.env` のRAKUCO_ID / RAKUCO_PASSを非表示で使う。MFの資格情報を取込送信V2や電子請求受付システムへ転用しない。
6. Windows操作は利用可能な `computer-use` スキルを読み、公式の操作APIを使用する。アプリ一覧にある取込送信V2を選択する。既知の実行ファイルは `C:/自立支援/取込送信V2/BIN/TS.exe`。対象ウィンドウと各操作後の状態を確認する。
7. ユーザーは本フローの通常ログイン自動化を指定済み。取込送信V2は2026-09-25にユーザーが両事業所用の共通パスワードを会話で明示し、沖洲ログインに使用済み。値はスキルに複写せず、利用可能なユーザー指定値または許可済みの秘密情報保存先から非表示で取得する。永続保存先は未設定。電子請求受付システムの送信用認証は別工程であり、この共通パスワードを転用しない。沖洲の許可済み.env取得元とキーは [取込・送信ルール](references/import-send-rules.md) に従う。呼出先スキルの一般的なログイン手動指定よりユーザーの明示指示を優先するが、上位制約や実際のツール拒否を回避しない。OTP・CAPTCHA・セキュリティ確認はユーザーへ引き継ぐ。
8. Googleドライブ操作は `google-drive:google-drive` を使用する。フォルダ名だけで決めず、親フォルダと事業所別の保存先を確認してフォルダIDを設定に残す。

## 取込・認証・本番送信の呼び出し

「国保連請求の取込」「送信前まで」「国保連請求を本番送信して」では [取込・送信ルール](references/import-send-rules.md) と [取込・送信フロー](references/import-send-flow.md) を読む。本番の標準終了点は送信→対応する営業所の認証情報選択→結果確認・エラー報告。取込のみ・模擬・送信禁止の実行は送信確認画面で止める。スキル化依頼や将来の本番手順説明は、現在の送信禁止を解除しない。

## 実行と送信前承認

1. ダウンロードルールに従い、川島・沖洲それぞれ対象月と全員選択を確認する。A・B別に作成・取得しない。人数は最新画面で確認する。
2. ダウンロードフローに従い、請求書・実績記録票を各営業所1組取得して全ファイルを精査し、内容を変えずに営業所番号付きでリネームする。ダウンロードのみの依頼はここで完了する。
3. 取込送信V2の事業所・請求年月とファイル対応を照合して取り込む。結果から情報種別ごとの送信件数・エラー件数を取得する。
4. 同じ事業所・提供月・請求年月について、ローカル実行記録と利用可能な送信履歴・到達確認を照合する。記録がないことだけで未送信と断定しない。送信済み・結果不明・照合不能の場合は送信を止めて確認する。
5. 送信前に、事業所名と番号、提供月、請求年月、利用者数、情報種別と送信件数、エラー件数、CSV識別情報、履歴確認結果を提示する。エラー0件・対象一致を確認してから承認を求める。承認はこの組合せに結びつけ、対象やCSVが変更された場合は再確認する。
6. 承認済みの内容を一度送信し、認証情報選択画面で沖洲は沖洲、川島は川島を選ぶ。直後の結果を確認し、エラーなら報告して停止する。到達結果と到達番号が表示されれば記録する。送信クリック成功だけで到達成功にしない。「正常に到達」は到達確認の状態として報告し、審査通過・支払確定と表現しない。
7. PDF保存・Drive格納も依頼された場合に限り、到達確認PDF、実績記録票PDF、請求書・明細書PDFを保存し、所定のドライブへ格納する。3種類の対象月・事業所・保存結果を確認して完了報告する。

## 記録と再開

- 単一事業所の全体実行は `runs/kokuho-claim/<提供年月>/<事業所番号>/<実行ID>/`、両営業所のダウンロードは `runs/kokuho-claim/<提供年月>/<実行ID>-download/<営業所>/` に保管する。リネーム前後の名前・元バイト列のハッシュを記録し、提出対象フォルダに元名と新名の同じCSVを併置しない。スキルフォルダに本番データを置かない。
- `run.json`は最低限、実行ID、対象事業所・年月、対象人数、工程、CSVのパスとハッシュ、取込件数とエラー件数、承認対象と日時、送信操作日時、到達状態と番号、PDF保存先とドライブID、未解決事項を持つ。資格情報・Cookie等を保存しない。
- 工程は `configured / csv_ready / imported / awaiting_approval / sending / arrived / archived` とし、例外は `blocked / arrival_unknown` と理由・最後に確認できた工程を記録する。送信前にsendingを記録して、中断後の無条件再送を防ぐ。
- 不一致・エラー時は依存する工程を止め、事実と必要な回答を短く質問する。権限や認証拒否を別経路で回避しない。
- 通信断や送信後の中断はarrival_unknownとし、画面・履歴・到達番号を確認する。未到達を確認できないまま再送しない。
- 到達済みで保存だけ失敗した場合は証憑保存から再開する。CSV作成・取込・送信をやり直さない。
- 再開時は保存記録だけでなく現在の画面・ファイルを確認し、既存PDFやドライブファイルを上書き・重複保存しない。

## 検証依頼

最初はアプリ起動と画面読取、認証、入力欄・ファイル選択、PDF保存の順に検証する。検証のために本番CSVを取り込んだり送信したりしない。取込検証には対象と取込の実行許可が必要。ダミー請求を国保連に送らない。実証した操作と未検証の工程を分けて報告し、実績に基づいてこのスキルを更新する。
